# ADR-0009: 有声书导出——合成循环在 Rust,输出分章 MP3 + manifest,不做 m4b

日期:2026-10-28
状态:已接受(实施随 B8 批次)

## 背景

plan-v0.3 B8 要把「听书」延伸为「导出有声书」。导出与播放的本质差异在数据量:
一本 10 万字的书合成后是数百 MB 音频,而播放管线(clipEngine)只同时持有
个位数音频块。若合成循环留在 webview,音频必须逐块过 IPC 落盘,既慢又占
webview 内存;若整书合成完再一次性传,更不可行。

## 考虑的选项

1. **合成循环在 webview,音频经 IPC 回传**:块级合成已有(edge_tts/tts.rs
   客户端都在 Rust,webview 只是编排),但音频字节每块都要跨一次 IPC,整书
   数百 MB 意味着数百次大负载往返;导出期间 webview 被自己的编排拖累,阅读
   卡顿风险高。
2. **合成循环在 Rust**:前端用 `tts-plan` 同套分块逻辑产出整书块清单
   (text + voice + 章节 index,一次 IPC 交付,几 MB 量级),Rust 侧复用
   现成的 edge_tts/tts.rs 合成与内容寻址缓存直接写盘。缓存复用使断点续跑
   免费(已合成块秒级跳过)。
3. **整书一次合成后封装 m4b**:需要 ffmpeg,违反 ADR-0001 依赖纪律
   (<100 行禁引依赖;ffmpeg 是量级完全不同的系统依赖)。

## 决策

选 2:**合成循环在 Rust,不在 webview**。

- 入口 `tts.export.start(bookHash, blocks, options)`,blocks 由前端一次交付;
- 输出 v1 = `<书名>-audiobook/` 目录:`chNN-章节名.mp3` + `manifest.json`
  (章节表/时长/文件偏移)。MP3 帧拼接即合法流,无需封装步骤;
- **m4b 不做**(需 ffmpeg,违反依赖纪律;留待 ADR 单独评估);
- 配套轻量任务系统:同书单任务、`task.progress/done/error` 事件、失败块重试
  1 次、取消即中断(已完成文件保留,下次续跑)、磁盘空间预检。

## 后果

- 导出期间正常阅读无卡顿(合成与写盘全在 Rust 侧后台线程);
- 断点续跑零额外实现成本(内容寻址缓存天然幂等);
- 产物是开放目录结构,任何播放器可按 manifest 章节定位;代价是不能在
  Apple Books/播客客户端里作为单文件有声书打开 —— 若未来需要,走独立 ADR
  评估封装层(可在 manifest 之上后置,不推翻本决策)。
- 事件协议首次扩展(`EventMap` 增 task.* 事件),协议文档同步更新。
