# ADR-0012: 跨书正文搜索维持 book_chunks 行表 + LIKE,不引入 FTS5

日期:2026-10-28
状态:已接受

## 背景

正文搜索(v10 迁移)把 AI 索引的 chunk 展开成 `book_chunks` 行表,搜索走
`LIKE '%q%' ESCAPE '\'` 的 C 层扫描。plan-v0.3 曾标注「FTS5 另行评估,不
承诺」。本 ADR 记录这次评估的结论与数据。

## 考虑的选项

1. **FTS5 + unicode61 分词器**:SQLite 默认。对中文**不切词** —— 连续汉字
   成为一个 token,用户查「灯芯」匹配不到含「灯芯偶尔响」的正文(整段才是
   一个 token,前缀/子串都够不着)。对以中文为主的个人书库,这是功能性
   否决,不是性能问题。
2. **FTS5 + trigram 分词器**(SQLite ≥3.34):支持子串匹配,但**查询至少要
   3 个字符** —— 中文搜索最常见的 2 字查询(「灯塔」「灯芯」)会返回空。
   且 trigram 索引体积约为原文的 2–3 倍,建索引成本显著。
3. **行表 + LIKE(现状)**:语义与旧行为完全一致(任意长度子串、ASCII 大小
   写不敏感),扫描在 SQLite 的 C 层完成,零解析零额外存储。

## 实测数据

`library::tests::search_like_benchmark`(默认 `#[ignore]`,本机可复跑):
60,000 行 / 18.1MB 中文正文(3 百本 × 2 百片),2 字 CJK 查询
**0.8 ms/次**(M 系列 MacBook,预热后 20 次均值)。

搜索入口有 200ms 防抖:0.8ms 比预算低两个多数量级;书库大十倍(180MB,
远超个人书库现实)也只要 ~8ms。

## 决策

维持 `book_chunks` 行表 + LIKE。引入 FTS5 的触发条件(重新评估的门槛):
- 书库行表超过 ~200MB 且实测 P95 > 50ms;或
- 出现对排序相关性(bm25)的真实需求。

## 后果

- 中文/英文任意子串搜索语义不变;无需索引维护(store_index 双写已覆盖)。
- 不引入 FTS5 虚表与 trigram 索引的体积/写放大。
- 若未来引入,迁移路径清晰:建 FTS5 虚表 + 回填一个事务,读路径换 MATCH,
  行表保留作离线兜底(与 RAG 的 retrieveByTerms 同一份 chunk 文本)。
